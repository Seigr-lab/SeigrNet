CHAPTER 02

SEIGRASM.

Project-owned native opcodes, senary notation, execution contracts and the foundation for Hyphos bootstrap.

Supporting experiments and qualification ↓

Purpose and execution boundary

SEIGRASM supplies project-owned instructions at the CPU execution boundary. Each implementation contains explicit native opcodes, operands and relative branch displacements. The CPU executes the corresponding bytes. Comments and source numeral spelling are not executed.

The current seed validates a senary representation of native instruction octets, writes those octets into a supplied memory region, performs instruction publication, and calls the resulting code. Publication means making preceding code writes available to subsequent instruction fetch on the executing core. The generated code can read and change memory and return a result.

The common contract is independent of a board name. Its realization depends on the selected instruction set, execution mode and available facilities. Identical input semantics must produce the same specified effect; the physical opcode bytes differ between architectures. Runtime resource discovery can follow a compatible initial entry. These images do not determine an unknown ISA before any compatible instructions have executed.

The target path contains no firmware request, OS service, external compiler, assembler, linker or host-language runtime. The supplied entry is callable machine code. It does not yet establish reset entry, a boot-medium handoff, memory mappings or initial stack storage, and therefore does not establish firmware-independent power-on boot.

Senary and execution contract

Source notation

Unmarked SEIGRASM literals are senary. Prefixes 0d, 0x and 0b select decimal, hexadecimal and binary. Thus 10, 0d6, 0x06 and 0b110 denote the same value. The native sources use explicit hexadecimal encodings to expose the instruction fields for ISA verification. Each token denotes a complete native word or octet according to the implementation. // introduces a source comment. Labels appearing in comments are explanatory only.

In-memory senary input

The entry consumes four numeric senary digits per output octet, most significant first. Each input digit occupies one octet whose value is between zero and five; it is not an ASCII character. An input group [1, 1, 0, 3] has value 255 and produces 0xff. The next group [1, 1, 0, 4] has value 256 and is rejected. Four digits are the smallest fixed senary group capable of representing every physical octet.

This grouping is a transport for the instruction bytes required by these CPUs. It does not define a Hyphos value width, Seigbit layer, Seigsit layout or physical six-state carrier. Senary notation and native instruction execution alone do not establish six electrical states.

Stable senary input→Full validation→Write opcode octets→Publish instructions→Call generated code

The source must be nonempty and its digit count divisible by four. Preparation checks required capacity, extent wraparound, intersection and instruction alignment before reading digits. It validates the entire input before writing the first destination octet. A second pass decodes the unchanged source into the destination. A preparation failure returns zero produced octets and performs no destination write or generated-code call.

Direct publication rejects an empty or wrapping executable extent; AArch64/RV64 also reject misalignment. Validation checks the transport and memory extents, not instruction legality or program safety. Supplied opcode content is trusted. Faults, non-returning payloads and concurrent mutation are outside this contract; they are not converted into the status values above.

Direct preparation uses the first four arguments; the fifth is used by the root entry. Counts, pointers and return registers follow the physical 64-bit ABI. Generated code must preserve the listed registers and stack, obey the selected calling convention and return normally. Other registers and arithmetic flags may change. No vector or floating-point preservation contract is established.

  • The initial execution mode must already match the image. AArch64 and RV64IM require four-octet-aligned entry and generated extent; this RV64 implementation does not support compressed instructions. x86-64 permits an unaligned generated entry.
  • Code, input, output and stack must be accessible normal memory. The destination must permit writing and execution. Input remains immutable throughout both passes. Used source, destination, seed and stack extents must be disjoint. Code checks source/destination intersection; the caller establishes the remaining memory conditions.
  • AArch64 and RV64 require a 16-octet-aligned incoming stack. For x86-64, incoming RSP modulo 16 is eight, with the return address at RSP; calls into generated code maintain that condition. The x86 seed uses no red zone. Reserve at least 48 octets below the incoming stack pointer for AArch64/RV64 seed frames, or 64 octets for x86-64, in addition to the generated program's own stack use.
  • The code does not configure exceptions, interrupts, translation, memory allocation or persistent storage. Any asynchronous handler or concurrent execution must preserve these entry conditions.

Architecture-specific publication

AArch64: read CTR_EL0, derive data and instruction line sizes independently, clean every intersecting data line with DC CVAU, execute DSB SY, invalidate every intersecting instruction line with IC IVAU, then execute DSB SY and ISB before the call. The execution level must permit those operations. This follows the cache publication requirements described by Arm's instruction-cache publication guidance.

x86-64: execute MFENCE, then the serializing CPUID instruction with leaf and subleaf zero, before the generated-code call. CPUID must be available at the entry privilege level. The Intel system programming manual, section on self-modifying code, specifies serialization between code modification and execution.

RV64IM + Zifencei: the decoder uses integer multiplication from M; publication executes FENCE RW,RW followed by FENCE.I. The RISC-V Zifencei specification defines instruction-fetch synchronization on the executing hart.

Each implementation publishes and calls on the same core or hart. Publication to other processors, memory aliases, device memory and concurrent code replacement require additional contracts and verification.

Physical qualification criteria

  1. Establish and record the initial execution mode, privilege, memory and stack conditions, including the mechanism that transfers control to the native image.
  2. Identify the installed source, seed image and payload bytes; recover target evidence of actual entry, decoded output, payload execution and return state.
  3. Repeat valid, altered-opcode and rejected-input cases with preserved evidence. Check the resulting memory state against the declared contract and account for the acquisition mechanism.
  4. Qualify each ISA on identified physical apparatus before extending an execution result to that implementation. Integrate the first Hyphos payload only with a declared semantic contract and observable acceptance criteria.

The three callable seeds retain their stated emulation qualification. The separate AArch64 electrical return records direct bus access and acquisition; it does not qualify the common seed contract on all three ISAs.
